# 部署、备份与恢复

## 1. 部署模型

生产环境由三个服务组成：

| 服务        | 公网可见  | 持久化内容                             |
| ----------- | --------- | -------------------------------------- |
| Caddy + Web | 仅 80/443 | TLS 状态使用 Docker 卷                 |
| Fastify API | 否        | 工作区根目录中的配置、对象、备份和报告 |
| PostgreSQL  | 否        | 工作区根目录下的 `database/postgres`   |

Caddy 负责 HTTPS、同源 `/api` 反向代理和安全响应头。API 与 PostgreSQL 只加入内部 Docker 网络。数据库密码通过 Docker secret 文件注入，不写入镜像、Git 或普通备份包。

## 2. 首次部署

以下命令以 Linux 服务器、域名 `workbench.example.com` 和工作区 `/srv/workbench` 为例。

### 2.1 准备域名和目录

把域名的 A/AAAA 记录指向服务器，并开放 TCP 80、TCP 443 和 UDP 443。安装 Docker Engine 与 Compose 插件后执行：

```bash
sudo install -d -o 1000 -g 1000 /srv/workbench
mkdir -p infra/secrets
umask 077
openssl rand -base64 36 > infra/secrets/postgres_password.txt
sudo chown 1000:1000 infra/secrets/postgres_password.txt
sudo chmod 600 infra/secrets/postgres_password.txt
```

API 容器使用 UID 1000 的非 root 用户运行。无论使用普通账户还是 `root` 部署，都必须让 UID 1000 可以读取数据库密码文件，同时不要放宽 `600` 权限。

创建不提交到 Git 的 `infra/.env.production`：

```dotenv
DOMAIN=workbench.example.com
DOMAIN_ALIAS_1=example.com
DOMAIN_ALIAS_2=www.example.com
WORKBENCH_HOST_ROOT=/srv/workbench
WORKBENCH_DB_NAME=workbench
POSTGRES_PASSWORD_FILE=./secrets/postgres_password.txt
WORKBENCH_ID=00000000-0000-4000-8000-000000000001
LOG_LEVEL=info
```

`DOMAIN` 是应用唯一的正式来源；两个可选别名只由 Caddy 接收，并永久跳转到正式域名。没有别名时可以省略 `DOMAIN_ALIAS_1` 和 `DOMAIN_ALIAS_2`。

### 2.2 初始化工作区、数据库和账户

```bash
docker compose --env-file infra/.env.production -f infra/compose.yaml build
docker compose --env-file infra/.env.production -f infra/compose.yaml up -d postgres
docker compose --env-file infra/.env.production -f infra/compose.yaml run --rm api \
  node apps/api/dist/entrypoints/cli.js workspace init
docker compose --env-file infra/.env.production -f infra/compose.yaml run --rm api \
  node apps/api/dist/entrypoints/cli.js db migrate
docker compose --env-file infra/.env.production -f infra/compose.yaml run --rm api \
  node apps/api/dist/entrypoints/cli.js auth init-owner
docker compose --env-file infra/.env.production -f infra/compose.yaml up -d
```

用户名固定为 `owner`，没有注册页面。最后一个命令会交互式读取密码并只保存 Argon2id 哈希。

### 2.3 健康检查

```bash
curl --fail https://workbench.example.com/health/live
curl --fail https://workbench.example.com/health/ready
docker compose --env-file infra/.env.production -f infra/compose.yaml ps
```

`live` 证明 API 进程存活；`ready` 还会检查数据库和固定账户是否就绪。HTTP 200 只表示部署健康，不替代登录和倒计时操作验收。

## 3. 日常备份

### 3.1 创建与校验

```bash
docker compose --env-file infra/.env.production -f infra/compose.yaml exec api \
  node apps/api/dist/entrypoints/cli.js backup create
docker compose --env-file infra/.env.production -f infra/compose.yaml exec api \
  node apps/api/dist/entrypoints/cli.js backup verify /srv/workbench/backups/local/<backup-directory>
```

备份包包含 PostgreSQL 自定义格式转储、完整 `config/` 配置树、对象文件、版本清单和逐文件 SHA-256 校验和。大文件校验使用流式读取，不会把整个附件一次性载入内存。`auth_sessions` 与 `auth_login_attempts` 只保留表结构、不备份数据；恢复后必须重新登录。

创建备份和孤立附件清理共用互斥锁：复制对象快照期间不会清理文件。上传仍可继续；内容寻址对象只会新增，因此数据库快照之后产生的额外对象不影响恢复一致性。失败的未完成备份目录会自动移除，不能被误当成可恢复备份。

本机 `backups/local` 不是唯一副本。至少把一份完成且校验通过的备份加密复制到服务器之外。数据库密码、TLS 私钥和其他 secrets 不进入普通备份包，应通过独立秘密管理方案恢复。

### 3.2 查看备份状态

设置页分别显示最近成功备份、最近校验和最近成功恢复时间。命令成功只说明对应步骤完成；只有在隔离环境完成真实恢复后，整条恢复链才能标记为 `VERIFIED`。

## 4. 附件容量与在线打开

- 通用附件单文件上限为 50 MiB，书籍封面额外限制为 5 MiB；空文件会被拒绝。
- 上传内容以流方式写入隔离目录并同步计算 SHA-256，超过限制或中断时删除临时文件，不把完整文件缓冲到 API 内存。
- PDF、常见安全图片和纯文本可以同源在线打开；其他 MIME 类型强制下载，并统一发送 `nosniff`。
- 下载支持 `Range`、`ETag`、`Last-Modified` 与准确的 `Content-Length`，PDF 拖动和断点读取不需要每次重传整个文件。
- 服务器磁盘仍是总容量上限。设置系统盘告警并把附件纳入异地备份；当附件规模长期接近服务器容量时，再迁移到 S3 兼容对象存储。

## 5. 恢复到新的空目标

恢复命令拒绝覆盖当前工作区，也拒绝非空目标数据库。以下示例先创建隔离数据库和空目录：

```bash
sudo install -d -o 1000 -g 1000 /srv/workbench-restored
docker compose --env-file infra/.env.production -f infra/compose.yaml exec postgres \
  createdb -U workbench workbench_restored
```

把目标目录额外挂载到一次性 API 容器；目标数据库密码继续从已有 Docker secret 读取：

```bash
docker compose --env-file infra/.env.production -f infra/compose.yaml run --rm \
  -e RESTORE_DATABASE_URL="postgres://workbench@postgres:5432/workbench_restored" \
  -e RESTORE_DATABASE_PASSWORD_FILE=/run/secrets/postgres_password \
  -v /srv/workbench-restored:/restore-target \
  api node apps/api/dist/entrypoints/cli.js backup restore \
  /srv/workbench/backups/local/<backup-directory> /restore-target
```

恢复流程会执行以下检查：

1. 验证备份格式、工作区 ID、必需文件和全部校验和；
2. 确认目标根目录和目标数据库为空；
3. 使用 `pg_restore --exit-on-error --single-transaction` 恢复数据库；
4. 执行当前版本迁移；
5. 再次清空 Session 与登录失败记录，并确认固定 `owner` 存在；
6. 恢复对象和配置，在 `migration-reports` 生成恢复报告。

检查报告和实际登录、倒计时数据、对象文件都通过后，才把正式流量切换到新工作区。切换时修改 `WORKBENCH_HOST_ROOT` 与 `WORKBENCH_DB_NAME`，再重新创建服务；保留旧实例只读，直到用户验收完成。

## 6. 更新与回滚

更新前必须先创建并校验完整备份，再拉取代码和迁移：

```bash
docker compose --env-file infra/.env.production -f infra/compose.yaml exec api \
  node apps/api/dist/entrypoints/cli.js backup create
docker compose --env-file infra/.env.production -f infra/compose.yaml exec api \
  node apps/api/dist/entrypoints/cli.js backup verify /srv/workbench/backups/local/<backup-directory>
git pull --ff-only
docker compose --env-file infra/.env.production -f infra/compose.yaml build
docker compose --env-file infra/.env.production -f infra/compose.yaml stop web api
docker compose --env-file infra/.env.production -f infra/compose.yaml run --rm api \
  node apps/api/dist/entrypoints/cli.js db migrate
docker compose --env-file infra/.env.production -f infra/compose.yaml up -d
```

镜像回滚只适用于数据库仍与旧版本兼容的情况。若新版本已经写入不兼容数据，应恢复到新的空工作区和数据库，而不是直接复制或降级正在运行的 PostgreSQL 数据目录。

## 7. 安全与使用边界

- 长期登录减少重复输入密码，但公共或临时设备不要勾选；可以在设置页查看、重命名和撤销设备会话。
- 登录 Cookie 使用 `Secure`、`HttpOnly` 和 `SameSite`，认证令牌不进入浏览器 Web Storage。
- 工作台没有注册、多用户、角色或功能级权限；不要把 API 端口直接暴露到公网来绕过 Caddy。
- 恢复 URL 默认不写密码，继续通过容器内的只读 secret 文件注入。
