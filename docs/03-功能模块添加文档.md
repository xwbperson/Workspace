# 功能模块添加文档（AI 执行版）

## 1. 文档用途

本文档用于指导 AI 在个人工作台中添加新功能。目标不是建设可热插拔的插件系统，而是在现有模块化单体中增加一个相对独立的纵向功能切片，使新增功能尽量不影响工作台主体和其他已完成功能。

AI 必须把以下内容视为约束，而不是建议：

- 所有功能继续一起构建、测试和发布，不创建微前端、独立服务或运行时插件系统。
- 新功能拥有自己的前端目录、后端目录、数据库表和测试。
- 工作台主体只通过固定注册点和公共贡献协议认识功能，不了解功能内部状态与表结构。
- 功能之间在视觉上仍然属于同一个应用，共享登录、导航、布局、设计语言、搜索、总览和通知。
- 普通新增功能不能顺手重写工作台壳、认证、备份、搜索、总览或其他功能。
- 只有一个固定 `owner` 账户，不添加注册、多用户、角色、租户或功能级权限。

如果本文档、代码和用户当前要求不一致，AI 必须先说明差异，以当前用户要求和仓库中的实际代码为准，不得静默假设。

## 2. 当前架构模型

工作台采用“模块化单体 + 纵向功能切片”：

```text
工作台公共平台
├── 登录与会话
├── PC / Android 响应式外壳
├── 总览、搜索、通知、快速创建
├── 偏好设置、备份与恢复
└── 功能注册与公共贡献协议
    ├── 倒计时（现有参考切片）
    ├── 新功能 A
    └── 新功能 B
```

用户不会看到“多个模块拼装成多个小应用”的割裂感。功能页面使用同一个壳；总览、搜索、通知等公共页面只渲染统一 DTO。功能通过公共协议贡献数据，而不是把自己的页面组件塞进工作台主体。

现有倒计时是实现参考，但不是要求所有功能机械复制。AI 应复制边界和接入方式，不应复制不适用的字段、状态或业务规则。

## 3. AI 开始编码前必须完成的检查

### 3.1 读取约束和当前状态

依次阅读：

1. 根目录 `AGENTS.md`；
2. `docs/01-架构文档.md`；
3. `docs/02-工作台主体设计文档.md`；
4. 本文档；
5. `apps/web/src/features/countdowns/`；
6. `apps/api/src/features/countdowns/`；
7. 三个固定注册点；
8. 当前最新数据库迁移和相关测试。

执行只读检查：

```powershell
git status --short
rg --files apps/web/src/features apps/api/src/features
rg --files apps/api/src/platform/database/migrations
```

AI 必须保留用户已有修改，不得覆盖、删除或回退无关文件。

### 3.2 先给出功能简报

编码前先用简短列表写明：

```text
功能名称：
featureId：
前端路由：
API 路径：
核心实体：
核心状态：
需要的公共能力：
是否产生通知：
是否需要定时任务：
是否需要文件存储：
预计新增文件：
预计修改的共享文件：
明确不修改的区域：
```

如果这些信息不足以确定数据模型或用户操作流程，应先向用户确认；如果只缺少不影响方向的小细节，可以采用保守默认值并明确记录。

## 4. 命名和身份规则

以下标识必须在前后端、路由、贡献和测试中保持一致：

| 项目        | 规则                                | 示例                          |
| ----------- | ----------------------------------- | ----------------------------- |
| `featureId` | 小写、稳定、建议使用复数 kebab-case | `countdowns`、`reading-notes` |
| 前端入口    | `/features/<featureId>`             | `/features/countdowns`        |
| API 资源    | `/api/v1/<resource>`                | `/api/v1/countdowns`          |
| 数据库表    | snake_case，并归属于功能            | `reading_notes`               |
| 查询键      | 以功能 ID 开头                      | `['reading-notes', 'list']`   |
| 总览块 ID   | `<featureId>:<block-name>`          | `countdowns:nearest`          |
| 通知 ID     | `<featureId>:<event>:<recordId>`    | `countdowns:reached:<uuid>`   |

`featureId` 一旦随数据发布，不应重命名或复用。路由中的记录 ID 必须使用 `encodeURIComponent`；数据库查询必须参数化。

## 5. 普通功能允许修改的范围

一个普通功能通常包含以下变更：

```text
apps/web/src/features/<featureId>/          新功能前端
apps/api/src/features/<featureId>/          新功能后端
apps/api/src/platform/database/migrations/  新迁移
packages/client-sdk/src/types.ts             共享 DTO
packages/client-sdk/src/client.ts            API 客户端方法
contracts/openapi.json                       命令生成，禁止手改
packages/client-sdk/src/generated/           命令生成，禁止手改
```

工作台主体通常只修改三个固定注册点：

```text
apps/web/src/app/feature-catalog.ts
apps/web/src/app/feature-routes.tsx
apps/api/src/app/feature-registry.ts
```

以下是按条件修改的共享文件：

| 条件                 | 允许的最小修改                                                              |
| -------------------- | --------------------------------------------------------------------------- |
| 使用新图标           | 扩展 `IconName`，并在 `apps/web/src/components/ui/FeatureIcon.tsx` 添加映射 |
| 新增数据库迁移       | 在 `apps/api/src/platform/database/migrations/index.ts` 末尾注册            |
| 新增总览公共数据形态 | 只有现有五种 `OverviewBlockData` 确实无法表达时才扩展共享契约和渲染器       |
| 第二个功能产生通知   | 修正通知页中的功能名称解析，不能继续硬编码“倒计时”                          |
| 新增备份数据         | 扩展真实 PostgreSQL 恢复验收，证明新表数据能恢复                            |

如果预计需要修改更多工作台主体文件，AI 必须先解释为什么公共协议不能满足需求。

## 6. 推荐目录结构

### 6.1 前端

```text
apps/web/src/features/<featureId>/
├── api.ts
├── <FeatureName>Page.tsx
├── components/
│   ├── <FeatureName>Form.tsx
│   └── <FeaturePrivateComponent>.tsx
├── hooks/                         # 确有复用时再创建
├── *.test.tsx
└── index.ts
```

- `api.ts` 封装功能 API、TanStack Query 键和失效策略。
- 页面负责视图状态与操作编排，不直接写 `fetch`。
- `components/` 只保存功能私有组件。
- `index.ts` 只导出工作台路由或其他功能确实需要的稳定表面。
- 不要为了“模块化”给每个小函数创建文件；没有复用价值时留在当前文件中。

### 6.2 后端

```text
apps/api/src/features/<featureId>/
├── repository.ts
├── service.ts
├── routes.ts
├── contributions.ts              # 按需实现公共贡献
├── notifications.ts              # 按需实现通知同步或调度
├── *.test.ts
└── index.ts
```

- `repository.ts`：参数化 SQL、数据库行映射，不承载业务决策。
- `service.ts`：输入归一化、状态流转、业务规则、并发冲突。
- `routes.ts`：HTTP 路径、认证声明、请求 Schema、状态码。
- `contributions.ts`：把功能私有数据转换为工作台公共 DTO。
- `notifications.ts`：功能私有的通知生成与定时任务；不要继续在平台目录增加带功能名的调度器。
- `index.ts`：稳定公开出口，不导出内部辅助函数。

## 7. 实施顺序

### 7.1 确定业务模型

至少明确：

- 实体及字段；
- 创建、读取、修改、完成、归档等操作；
- 合法状态和状态转换；
- 空数据与已归档数据如何处理；
- 哪些数据应进入总览、搜索、最近内容或通知；
- 并发修改如何处理；
- PC 与 Android 上的主要操作路径。

默认采用软归档，不直接物理删除重要记录。可修改实体建议包含 `version`，写操作通过预期版本实现乐观并发；冲突使用 `ConflictError`，不存在使用 `NotFoundError`。

### 7.2 创建数据库迁移

1. 检查当前迁移最大编号，不得预先假设下一个一定是 `003`。
2. 新建 `<next>-<feature-name>.ts`。
3. 为状态、长度、数值范围添加数据库约束。
4. 为列表、搜索、时间排序等真实查询添加索引。
5. 在 `migrations/index.ts` 末尾导入并追加新迁移。

禁止修改已经发布的迁移。迁移必须可以从空数据库按顺序执行；不得依赖开发机手工创建的表或字段。

新增迁移后应检查：

- `apps/api/src/platform/backup/backup-service.test.ts` 中的最新迁移版本断言；
- `scripts/validate-real-postgres.ts` 中的写入和恢复后数量/不变量检查。

逻辑备份会包含新表，但只有恢复测试实际写入并验证新功能数据，才能声称该功能的迁移能力已验证。

### 7.3 实现后端切片

推荐顺序：

1. 定义数据库行类型与仓库；
2. 实现服务层规则；
3. 定义 API 路由和 Schema；
4. 添加服务或路由测试；
5. 实现工作台公共贡献；
6. 在后端注册表组装依赖。

每个功能路由必须：

- 使用 `/api/v1/...`；
- 配置 `config: { authenticated: true }`；
- 对 `params`、`querystring` 和 `body` 提供 Schema；
- 对对象请求使用 `additionalProperties: false`；
- 明确必填字段、长度、枚举和数值边界；
- 返回统一的 `AppError`、`NotFoundError` 或 `ConflictError`；
- 不记录密码、Cookie、CSRF Token 或完整敏感请求体。

认证钩子会统一执行会话、同源和 CSRF 校验。功能不得新增绕过认证的写接口。

### 7.4 更新共享 SDK 和 OpenAPI

在 `packages/client-sdk/src/types.ts` 添加功能 DTO，在 `client.ts` 添加客户端方法。前端功能必须通过共享 `workbenchClient` 请求 API，不直接复制请求、Cookie 或 CSRF 逻辑。

路由 Schema 完成后执行：

```powershell
npm run openapi:generate
```

该命令会更新：

```text
contracts/openapi.json
packages/client-sdk/src/generated/openapi.d.ts
```

禁止手工编辑上述生成文件。生成后检查差异，确认新增路径、请求和响应符合预期，没有意外删除旧接口。

### 7.5 实现前端切片

前端至少处理以下界面状态：

- 首次加载；
- 空数据；
- 局部加载失败和重试；
- 表单校验；
- 保存中和重复提交保护；
- 保存成功后的缓存刷新；
- 版本冲突提示；
- 归档或不可用状态；
- 直接刷新详情路由。

查询键必须以功能 ID 为命名空间。写操作成功后按真实影响失效缓存：

```text
功能列表 / 详情
工作台总览        # 功能贡献了总览、关注、未来或最近内容时
工作台通知        # 写操作会改变通知时
工作台搜索        # 已存在相关搜索缓存时
```

不要通过刷新整个页面解决缓存问题。

页面应复用现有工作台布局、按钮、表单、提示和颜色变量。不要给功能建设独立导航、独立主题或另一套移动端壳。PC 与 Android 可以采用不同排布，但必须共享同一套路由、数据和业务逻辑。

### 7.6 选择公共贡献能力

功能目录中的能力声明必须和后端实际实现一致：

| 前端 `capabilities` | 后端实现               | 显示位置               |
| ------------------- | ---------------------- | ---------------------- |
| `focusCandidates`   | `getFocusCandidates()` | 总览“当前关注”         |
| `upcoming`          | `getUpcoming()`        | 总览未来时间轨道       |
| `recent`            | `getRecent()`          | 总览最近内容           |
| `overviewBlocks`    | `overviewBlocks`       | 可排序、可隐藏的摘要块 |
| `search`            | `search`               | 全局搜索结果           |
| `quickCreate`       | `quickCreateActions`   | 快速创建面板           |
| `notifications`     | 通知同步或调度         | 通知中心和未读数量     |

只实现有真实价值的能力。没有对应数据时，省略字段和实现；不要返回假数据、空占位卡片或永远为空的搜索组。

公共贡献只能返回 `packages/client-sdk/src/types.ts` 中定义的统一 DTO。总览页面不能导入功能组件，功能贡献也不能返回 React 节点或私有数据库对象。

总览块优先使用现有数据形态：

```text
metric
progress
recent-list
upcoming
status
```

只有两个以上功能出现同一种、且现有类型无法表达的需求时，才扩展共享类型和公共渲染器。

### 7.7 更新三个固定注册点

#### 前端功能目录

在 `apps/web/src/app/feature-catalog.ts` 添加一项：

```ts
{
  featureId: '<featureId>',
  name: '<中文名称>',
  description: '<一句话说明>',
  icon: '<IconName>',
  route: '/features/<featureId>',
  category: '<FeatureCategory>',
  keywords: ['<搜索词>'],
  order: 20,
  lifecycle: 'in-development',
  discoverableInProduction: false,
  canPin: true,
  capabilities: {
    search: true,
  },
}
```

开发未完成时使用 `in-development` 和 `discoverableInProduction: false`。只有功能、测试和接入均完成后才改为 `released` 和 `true`。

目录会自动驱动功能汇总、固定功能和导航，不要为普通功能手工修改 `WorkbenchShell`、`FeaturesPage` 或 `navigation.ts`。

如需新图标，同时扩展 `IconName` 和 `FeatureIcon.tsx`。当前 `FeatureIcon` 的回退图标会掩盖漏配问题，因此测试或人工检查必须确认实际图标正确。

#### 前端路由

当前项目使用静态导入，不要声称已经实现懒加载。按现有模式修改 `apps/web/src/app/feature-routes.tsx`：

```tsx
import { FeaturePage } from '../features/<featureId>/index.js';

export const featureRoutes = [
  // existing routes
  { path: 'features/<featureId>', element: <FeaturePage /> },
  { path: 'features/<featureId>/:recordId', element: <FeaturePage /> },
] as const;
```

只添加功能实际需要的路由。功能页面实现留在功能目录中。

#### 后端功能注册表

在 `apps/api/src/app/feature-registry.ts` 的组合根中创建仓库、服务并追加注册项：

```ts
const featureRepository = new FeatureRepository(database);
const featureService = new FeatureService(featureRepository);

{
  featureId: '<featureId>',
  contribution: createFeatureContributions(featureRepository),
  registerRoutes: async (app) => registerFeatureRoutes(app, featureService),
  syncNotifications: async () => {},
  startScheduler: () => () => {},
}
```

当前 `FeatureRegistration` 要求通知生命周期函数存在。无通知功能只在注册项中使用上述最小空实现，不要创建空的 `notifications.ts`。如果后续多个无通知功能都出现相同空实现，可另行把接口改为可选，但不能把这项平台重构混入第一个普通功能。

如果功能需要通知，则从功能自己的 `notifications.ts` 导入同步与调度函数。`startScheduler` 必须返回停止函数，应用关闭时用于释放定时器。

## 8. 通知接入规则

通知必须写入共享 `NotificationRepository`，不得建设功能私有通知中心。

通知至少包含：

- 稳定且可去重的 `notificationId`；
- `source: { kind: 'feature', featureId: '<featureId>' }`；
- 类型、严重程度、标题和发生时间；
- 可选摘要与目标路由；
- 是否需要用户操作。

调度任务必须幂等，同一业务事件重复扫描不能生成重复通知。轮询失败应交给注册表传入的 `onError`，不能导致整个 API 退出。

当前 `apps/web/src/app/pages/NotificationsPage.tsx` 对功能来源名称存在“倒计时”硬编码。添加第二个会产生通知的功能时，必须把它改为根据 `notification.source.featureId` 查询 `featureCatalog`，这是必要且范围明确的共享修正。

## 9. 功能之间如何调用

### 9.1 首选方式

- 展示其他功能内容：通过工作台贡献 DTO 聚合。
- 跳转到其他功能：使用稳定路由。
- 快速创建：使用 `QuickCreateActionDefinition`。
- 共享通知：使用 `NotificationRepository`。
- 共享基础能力：放在 `platform/`，但必须是至少两个功能的真实共同需求。

### 9.2 允许的直接业务调用

如果功能 A 确实需要调用功能 B 的业务能力：

1. B 从自己的 `index.ts` 导出一个窄而稳定的接口；
2. 在 `feature-registry.ts` 或应用组合根中注入依赖；
3. A 不导入 B 的 `repository.ts`、私有组件或内部辅助函数；
4. A 不直接读取或写入 B 的数据库表；
5. 添加跨功能契约测试，并说明失败和事务边界。

不要为了可能出现的未来需求预先建设事件总线、服务定位器或通用插件 API。

## 10. 测试要求

### 10.1 最低自动化测试

每个功能按风险至少覆盖：

- 服务层的核心状态转换和非法输入；
- 仓库或 API 的创建、读取、修改、冲突和归档；
- 关键前端组件或用户操作；
- 功能目录中的 ID、路由和能力声明；
- 公共贡献的数据映射；
- 声明的总览、搜索、快速创建或通知接入；
- 新迁移和备份恢复不变量。

`apps/web/src/app/feature-catalog.test.ts` 当前包含“只有一个首发功能”的断言。添加新功能时必须有意识地更新该测试，不能只为了通过测试而删除唯一性和路由检查。

API 集成测试可以扩展 `apps/api/src/app/build-app.test.ts`，也可以在功能目录创建更聚焦的路由测试。测试数据库可以使用项目现有内存数据库；真实 PostgreSQL 差异由专用恢复验证和 GitHub Actions 覆盖。

### 10.2 必须运行的命令

```powershell
npm run openapi:generate
git diff -- contracts/openapi.json packages/client-sdk/src/generated/openapi.d.ts
npm run check
```

如果修改了迁移、备份或恢复逻辑，还必须确保 GitHub Actions 中的真实 PostgreSQL 恢复任务通过。不要绕过 `scripts/validate-real-postgres.ts` 的 CI 临时数据库保护去连接个人数据库。

### 10.3 本地人工验收

可使用根目录临时运行脚本：

```powershell
workbench-local.bat start
workbench-local.bat status
workbench-local.bat stop
```

至少检查：

1. 固定 `owner` 账户可以登录；
2. 功能汇总页出现正确方格、名称、分类和图标；
3. PC 导航和 Android 布局入口可用；
4. 列表、创建、编辑、冲突、空状态和归档符合设计；
5. 直接刷新详情路由不会回到首页；
6. 声明的总览、搜索、快速创建和通知能力确实可用；
7. 一个功能失败不会阻断其他总览来源；
8. 浏览器宽屏和约 `390 x 844` 的 Android 视口均可操作。

临时运行脚本使用内存数据库，停止后数据消失，不能用于验证跨重启持久化或正式备份恢复。

## 11. AI 禁止事项

添加普通功能时禁止：

- 建设动态插件加载、模块市场、微前端或独立后端服务；
- 添加注册、多用户、角色、租户或功能级权限；
- 修改已经发布的数据库迁移；
- 直接读取或写入其他功能的私有表；
- 从工作台主体导入功能私有组件或状态；
- 让功能自己处理 Cookie、Session Token 或 CSRF Token；
- 手工编辑 OpenAPI 生成文件；
- 为单个功能提前抽象大型共享框架；
- 为通过测试而删除有价值的旧断言；
- 用全页刷新代替正确的缓存失效；
- 在共享页面硬编码某个功能名称；
- 顺手重构无关功能、认证、备份或工作台壳；
- 未经用户要求执行提交、推送、部署、数据删除或正式恢复。

## 12. 完成判定

只有同时满足以下条件，AI 才能报告功能实现完成：

- 功能业务闭环可用，不是只有页面或接口骨架；
- 前后端切片和数据库迁移完整；
- 三个固定注册点已接入；
- 目录能力声明与后端贡献一致；
- PC 和 Android 共用逻辑并可操作；
- OpenAPI 和 SDK 已更新；
- 自动化测试覆盖核心行为；
- `npm run check` 实际通过；
- 迁移相关变更通过真实 PostgreSQL 恢复验证，或明确标记尚待 CI 验证；
- 没有覆盖用户原有修改；
- 没有把 AI 生成代码描述成用户已经验收。

状态用语：

- `PREPARED`：代码或文档已生成，但相关验证未执行或未通过；
- `VERIFIED`：明确列出的自动化检查实际通过；
- `ACCEPTED`：用户实际使用后确认符合需求。

## 13. AI 交付报告模板

完成任务后按以下结构报告：

```text
结果：实现了什么，用户从哪里进入。

新增：
- 前端切片
- 后端切片
- 数据库迁移
- 公共贡献

主体修改：
- 修改了哪三个注册点
- 是否存在额外共享修改及原因

验证：
- 实际执行的命令及结果
- 已验证的 PC / Android 操作
- 备份恢复是否由真实 PostgreSQL 验证

边界：
- 尚未验证或需要用户验收的内容
- 没有执行的提交、推送或部署
```

报告必须具体说明“验证了什么”和“没有验证什么”，不能只写“全部完成”。
